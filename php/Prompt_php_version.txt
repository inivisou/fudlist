## 🧠 CONTEXTO GENERAL DEL PROYECTO

Aplicación web para la gestión y generación de menús semanales, accesible desde navegador y como aplicación nativa en Android (APK).

Principios fundamentales:
- Arquitectura Híbrida: Backend PHP + MariaDB en servidor remoto, Frontend Web completo, App Android encapsulada con Capacitor/Cordova.

## 🗂️ ESQUEMA DE BASE DE DATOS (MARIA DB)

### 1. Tabla `users`
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    nombre_completo VARCHAR(100),
    avatar_url VARCHAR(255),
    activo BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

### 2. Tabla `preferencias_usuario`
CREATE TABLE preferencias_usuario (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario_id INT NOT NULL,
    clave VARCHAR(50) NOT NULL,
    valor TEXT NOT NULL,
    tipo_dato ENUM('json', 'string', 'boolean', 'integer') DEFAULT 'string',
    descripcion VARCHAR(255),
    FOREIGN KEY (usuario_id) REFERENCES users(id) ON DELETE CASCADE,
    UNIQUE KEY unique_usuario_clave (usuario_id, clave)
);
Claves predefinidas:
- ingredientes_a_evitar: Array JSON de IDs de ingredientes que el usuario no quiere consumir.
- restriccion_dietetica: String (ej: vegetariano, celiaco, sin lactosa).
- platos_exclusivos: Array JSON de IDs de platos que son exclusivos para este usuario.
- platos_preferidos: Array JSON de IDs de platos que este usuario prefiere.

### 3. Tabla `ingredientes`
CREATE TABLE ingredientes (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) UNIQUE NOT NULL,
    calorias_x_100g DECIMAL(5,2) NOT NULL DEFAULT 0.00,
    supermercado VARCHAR(100) DEFAULT 'General',
    categoria VARCHAR(50) DEFAULT 'general',
    activo BOOLEAN DEFAULT TRUE
);

### 4. Tabla `platos`
CREATE TABLE platos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(150) NOT NULL,
    tipo ENUM('sopa', 'principal', 'postre', 'ensalada', 'guarnicion') DEFAULT 'principal',
    categoria VARCHAR(50),
    es_comida BOOLEAN DEFAULT TRUE,
    es_cena BOOLEAN DEFAULT FALSE,
    nivel_calorico ENUM('bajo', 'medio', 'alto') DEFAULT 'medio',
    activo BOOLEAN DEFAULT TRUE
);

### 5. Tabla `recetas`
CREATE TABLE recetas (
    id INT AUTO_INCREMENT PRIMARY KEY,
    id_plato INT NOT NULL,
    titulo_html TEXT,
    subtitulo_html TEXT,
    texto_html LONGTEXT,
    enlace VARCHAR(255),
    herramientas JSON,
    FOREIGN KEY (id_plato) REFERENCES platos(id) ON DELETE CASCADE
);

### 6. Tabla `recetas_ingredientes`
CREATE TABLE recetas_ingredientes (
    id INT AUTO_INCREMENT PRIMARY KEY,
    id_receta INT NOT NULL,
    id_ingrediente INT NOT NULL,
    cantidad DECIMAL(10,2) DEFAULT 1.0,
    unidad VARCHAR(20) DEFAULT 'g',
    FOREIGN KEY (id_receta) REFERENCES recetas(id) ON DELETE CASCADE,
    FOREIGN KEY (id_ingrediente) REFERENCES ingredientes(id) ON DELETE RESTRICT,
    UNIQUE KEY unique_receta_ingrediente (id_receta, id_ingrediente)
);

### 7. Tabla `menus`
CREATE TABLE menus (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario_creador_id INT NOT NULL,
    nombre VARCHAR(100) NOT NULL,
    tipo ENUM('actual', 'favorito') DEFAULT 'actual',
    fecha_generacion TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    fecha_inicio DATE,
    fecha_fin DATE,
    FOREIGN KEY (usuario_creador_id) REFERENCES users(id) ON DELETE CASCADE
);

### 8. Tabla `menu_comensales`
CREATE TABLE menu_comensales (
    id INT AUTO_INCREMENT PRIMARY KEY,
    id_menu INT NOT NULL,
    id_usuario INT NOT NULL,
    FOREIGN KEY (id_menu) REFERENCES menus(id) ON DELETE CASCADE,
    FOREIGN KEY (id_usuario) REFERENCES users(id) ON DELETE CASCADE,
    UNIQUE KEY unique_menu_usuario (id_menu, id_usuario)
);

### 9. Tabla `menu_dias`
CREATE TABLE menu_dias (
    id INT AUTO_INCREMENT PRIMARY KEY,
    id_menu INT NOT NULL,
    dia_numero TINYINT NOT NULL, -- CAMBIO: Número correlativo (1, 2, 3...) NO día de semana
    tipo_momento ENUM('comida', 'cena') NOT NULL,
    id_plato INT,
    FOREIGN KEY (id_menu) REFERENCES menus(id) ON DELETE CASCADE,
    FOREIGN KEY (id_plato) REFERENCES platos(id) ON DELETE SET NULL,
    UNIQUE KEY unique_dia_momento (id_menu, dia_numero, tipo_momento)
);

### 10. Tabla `platos_favoritos`
CREATE TABLE platos_favoritos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario_id INT NOT NULL,
    id_plato INT NOT NULL,
    creado_en TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (usuario_id) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY (id_plato) REFERENCES platos(id) ON DELETE CASCADE,
    UNIQUE KEY unique_usuario_plato (usuario_id, id_plato)
);

### 11. Tabla `ingredientes_comprados`
CREATE TABLE ingredientes_comprados (
    id INT AUTO_INCREMENT PRIMARY KEY,
    id_menu INT NOT NULL,
    id_ingrediente INT NOT NULL,
    comprado BOOLEAN DEFAULT FALSE,
    FOREIGN KEY (id_menu) REFERENCES menus(id) ON DELETE CASCADE,
    FOREIGN KEY (id_ingrediente) REFERENCES ingredientes(id) ON DELETE CASCADE,
    UNIQUE KEY unique_menu_ingrediente (id_menu, id_ingrediente)
);

## 🧩 LÓGICA DE NEGOCIO COMPLETA (VERIFICADA CONTRA EL ORIGINAL)

### 1. AUTENTICACIÓN Y MULTIUSUARIO
- Registro seguro con password_hash() (PASSWORD_BCRYPT).
- Login con sesiones seguras (SESSION con cookies HttpOnly y Secure).
- Todos los datos filtrados por usuario_id.
- Un usuario solo ve sus propios menús y favoritos.

### 2. GESTIÓN DEL MENÚ ACTUAL (ÚNICO)
- Generación: Al pulsar Generar, se busca el menú existente del usuario con tipo='actual'.
  - Si existe: Se borran sus registros en menu_dias y menu_comensales.
  - Si no existe: Se crea uno nuevo con tipo='actual' y un nombre genérico (ej: Menú Actual).
- Sobrescritura: El nuevo menú reemplaza al anterior. Solo hay uno por usuario.
- Edición: El usuario puede editar este menú en tiempo real.

### 3. GESTIÓN DE MENÚS FAVORITOS (MÚLTIPLES)
- Guardar como Favorito:
  - El usuario pulsa Guardar como Favorito en el menú actual.
  - Se solicita un nombre para el menú (ej: Menú de Verano, Menú Vegano).
  - Se crea un NUEVO registro en menus con tipo='favorito' y el nombre proporcionado.
  - Se copian todos los registros de menu_dias y menu_comensales del menú actual al nuevo favorito.
  - El menú actual sigue existiendo y se puede seguir editando/generando.
- Listado: El dashboard muestra una lista de todos los favoritos del usuario con su nombre personalizado.
- Cargar Favorito: Al hacer clic en un favorito, se carga su contenido en una vista de solo lectura o edición.

### 4. GESTIÓN DE PLATOS FAVORITOS
- Marcar/Desmarcar: En la lista de platos o en la vista de receta, el usuario puede marcar un plato como favorito.
- Almacenamiento: Se inserta/borra en platos_favoritos.
- Uso en Generación: Dar prioridad a los platos favoritos del usuario o de los comensales seleccionados.

### 5. DOS MENÚS TOTALMENTE DIFERENCIADOS (REGLA CRÍTICA DEL ORIGINAL)

#### 5.1. MENÚ TENTATIVO (GENERADO)
- Se genera al pulsar Generar.
- Cumple TODAS las restricciones.
- NO repetidos.
- NO editable.
- NO tiene checkboxes.
- Es efímero.
- Se resetea completamente cada vez que se pulsa Generar.
- **FORMATO DE TABLA EXACTO DEL ORIGINAL:**
Nº | Comida | Para | Cena | Para

- Columna "Para": Muestra qué comensales pueden comer ese plato (basado en preferencias/exclusivos).
- Ejemplo: "Eme / Cris" o solo "Eme" o solo "Cris".
- No hay checkboxes.
- Click sobre la **celda** (no botón) añade al menú efectivo.
- **Visualización:** Mostrar el plato con su nombre, calorías y etiqueta del nivel_calorico.

#### 5.2. MENÚ EFECTIVO (SELECCIONADO POR EL USUARIO)
- Vive en la base de datos (menu_dias).
- Editable.
- Puede contener repetidos (el usuario puede modificarlo).
- Tiene checkboxes para quitar platos.
- Es la base para:
- Lista dinámica de ingredientes.
- Generación del PDF.
- Al pulsar Generar de nuevo:
- El menú tentativo se reinicia.
- El menú efectivo SE MANTIENE INTACTO (hasta que el usuario lo modifique).
- **FORMATO DE TABLA EXACTO DEL ORIGINAL:**
Día | Comida | Quitar | Cena | Quitar | Herramientas del Día

- Los días son **números correlativos**, empezando en 1, **SIN FECHAS** (1, 2, 3, 4...).
- Checkboxes para quitar platos.
- Columna "Quitar": Checkbox que elimina la comida o cena, dejando el hueco libre.
- El hueco libre puede volver a rellenarse desde el tentativo.
- Columna "Herramientas del Día": Resumen consolidado de herramientas para comida + cena.

### 6. INTERACCIÓN CON EL MENÚ TENTATIVO (DEL ORIGINAL)
- Click en celda de comida → añade comida al menú efectivo.
- Click en celda de cena → añade cena al menú efectivo.
- Se coloca en el **primer hueco libre** (primera fila donde falte comida o cena).
- Mostrar alerta visual:
- "Comida añadida"
- "Cena añadida"
- **IMPORTANTE:** No se añade al final, se busca el primer hueco vacío.

### 7. INTERACCIÓN CON EL MENÚ EFECTIVO (DEL ORIGINAL)
- Checkboxes en cada plato para quitarlo.
- Al desmarcar: se elimina la comida o cena, el hueco queda libre.
- El hueco puede volver a rellenarse desde el tentativo.
- Los días son correlativos (1, 2, 3...), no días de la semana.

### 8. CONTROLES DE ENTRADA (GENERACIÓN) - DEL ORIGINAL
- Selector múltiple "No contenga herramientas":
- Texto: "No contenga herramientas"
- Opciones: herramientas únicas de recetas.
- Excluye recetas con esas herramientas.
- Input numérico "Días":
- Texto: "Días"
- Entero obligatorio.
- Mínimo: 1.
- Máximo: total_platos / 2.
- Botón "Generar".

### 9. SELECCIÓN DE COMENSALES
- Checkbox list con todos los usuarios activos.
- Se guardan en menu_comensales.
- Las preferencias de TODOS los comensales se unifican para la generación.

### 10. RECOPIACIÓN DE RESTRICCIONES
- Se consultan las preferencias de TODOS los comensales seleccionados.
- Se unifican los ingredientes_a_evitar de todos (un plato se excluye si ALGÚN comensal evita ese ingrediente).
- Se identifican restricciones dietéticas comunes.
- Se identifican platos exclusivos de cada comensal.

### 11. RESTRICCIONES DE GENERACIÓN (CRÍTICO - DEL ORIGINAL)
- No repetir platos en el mismo menú (salvo necesidad extrema).
- ≥ 4 días entre pasta.
- ≥ 9 días entre fajitas.
- ≥ 5 días entre tortillas.
- ≥ 5 días entre cremas.
- Al menos un pescado cada 7 días.
- Excluir platos que contengan ingredientes en ingredientes_a_evitar de CUALQUIER comensal.
- Excluir platos que no cumplan restricciones dietéticas de CUALQUIER comensal.
- Respetar filtros de herramientas (excluir recetas que usen herramientas seleccionadas).

### 12. LÓGICA DE PERSONAS (COMENSALES) - DEL ORIGINAL
- Mantener platos exclusivos: Si un plato es exclusivo de un comensal, solo aparece para ese comensal.
- Añadir complemento si coincide el día: Si dos comensales tienen platos diferentes el mismo día, añadir complemento si es necesario.
- **Prioridad:**
1. Exclusivo (plato que solo puede comer un comensal específico).
2. Compartido (plato que pueden comer todos).
- **Columna "Para" en Menú Tentativo:** Mostrar qué comensales pueden comer cada plato (ej: "Eme / Cris" o "Eme" o "Cris").

### 13. RESOLUCIÓN DE INGREDIENTES - DEL ORIGINAL
- Buscar por coincidencia exacta de nombre (ahora por ID).
- Si no existe en el catálogo:
- Se acepta igualmente.
- supermercado = "Desconocido".
- Nunca se rompe la ejecución.

### 14. CÁLCULO DE CALORÍAS
- Fórmula: Calorías Totales = SUM( (cantidad * calorias_x_100g) / 100 ).
- Se asume que la unidad por defecto es gramos (g).
- Si la unidad es diferente (ej: kg), se debe convertir a gramos antes del cálculo.
- Si un ingrediente no tiene calorias_x_100g definido (NULL o 0), se asume 0 calorías para ese ingrediente.
- Visualización en el Menú:
- Menú Tentativo: Mostrar las calorías totales del plato entre paréntesis (ej: Sopa de cocido (450 kcal)).
- Menú Efectivo: Mostrar las calorías totales del plato en la celda correspondiente.
- **NUEVO:** El campo nivel_calorico en la tabla platos se usa para pintar visualmente el plato (clases CSS: .cal-bajo, .cal-medio, .cal-alto).

### 15. LISTA DINÁMICA DE INGREDIENTES (CON GESTIÓN DE INVENTARIO)
- Se actualiza en tiempo real (AJAX).
- Basada SOLO en el menú efectivo.
- Ingredientes agrupados por nombre.
- **FORMATO DEL ORIGINAL:**
Día 1 – Comida · Filetes de lomo · Caldo de cocido · Fideos · Sal

- **Columna "Ya en casa":** Al final de cada fila de ingrediente, añadir un CHECKBOX.
- Si se marca: El ingrediente se registra en la tabla ingredientes_comprados como comprado = TRUE.
- Visualmente: El ingrediente tachado o con opacidad reducida.
- El PDF de la lista de la compra debe EXCLUIR los ingredientes marcados como "comprados".
- Ordenar por supermercado.

### 16. RESUMEN DE HERRAMIENTAS DIARIAS
- En el Menú Efectivo, en la columna final de cada día:
- Consultar las herramientas de la receta de la Comida.
- Consultar las herramientas de la receta de la Cena.
- Unificar y deduplicar la lista (ej: Comida="Olla", Cena="Sartén" → Resultado: "Olla, Sartén").
- Mostrar esta lista compacta en la celda.

### 17. PDF DE INGREDIENTES
- Dos opciones:
- Vista previa (nueva pestaña).
- Descargar.
- Contenido:
- Ingredientes únicos.
- Ordenados por supermercado.
- **FILTRO:** Solo incluir ingredientes donde comprado = FALSE.
- Recomendación: Usar TCPDF o Dompdf para generación profesional.
- Opcional: Incluir resumen calórico diario en el PDF.

### 18. VISTA DE RECETA (receta.php) - DEL ORIGINAL
- Recibe id como parámetro (?id=1).
- Lee de recetas (JOIN con platos).
- Renderiza:
1. titulo_html (enlace externo, target="_blank").
2. subtitulo_html.
3. texto_html.
4. Lista de ingredientes (con cantidad y unidad explícitas).
5. Lista de herramientas.
- Toda la estructura HTML la genera PHP.
- Botón "Marcar como favorito" para el plato.
- Mostrar calorías totales de la receta en la vista.
- Mostrar nivel_calorico visual.

## 🚦 RESTRICCIONES TÉCNICAS Y DE SEGURIDAD

1. Integridad del Menú Actual: Asegurar que un usuario nunca tenga más de un menú con tipo='actual'. Usar transacciones SQL o lógica de aplicación robusta.
2. Copiado de Favoritos: Al guardar un favorito, debe ser una copia profunda (clonar menu_dias y menu_comensales), no una referencia.
3. SQL Injection: PDO::prepare() obligatorio para TODAS las consultas.
4. XSS: htmlspecialchars() en todas las salidas.
5. Librerías: Solo para PDF (TCPDF/Dompdf) y Empaquetado (Capacitor/Cordova). Justificar uso en comentarios.
6. Validación: Validar entradas en PHP (backend) y JS (frontend).
7. Accesibilidad: WCAG 2.2 obligatorio.
8. Navegación por teclado: Tablas accesibles.
9. Responsive: CSS Grid/Flexbox para móvil y escritorio.
10. Sin jQuery: fetch() nativo para AJAX.
11. Manejo de errores: try-catch en PDO, mensajes claros al usuario.
12. Validación JSON: Validar estructura de datos JSON antes de usar.
13. HTTPS Obligatorio: Para la app híbrida y la API, el tráfico debe ir cifrado.
14. CORS: Configurar cabeceras CORS en el servidor PHP para permitir peticiones desde el contenedor de la app si se usa una URL externa.
15. Precisión de Calorías: Asegurar que el cálculo de calorías sea preciso y maneje casos donde calorias_x_100g sea 0 o NULL.
16. Formato de Calorías: Mostrar como entero redondeado (ej: 450 kcal) o con un decimal si se desea precisión.
17. **Gestión de Estado de Ingredientes:** El checkbox "Ya en casa" debe persistir en la BD (ingredientes_comprados) y actualizarse vía AJAX sin recargar la página.
18. **Consolidación de Herramientas:** La lógica de unión de herramientas por día debe ser eficiente (SET de herramientas en PHP o SQL).
19. **Visualización de Nivel Calórico:** Usar clases CSS específicas (ej: .cal-bajo, .cal-alto) para colorear o añadir iconos según el campo nivel_calorico.
20. **Primer Hueco Libre:** Al añadir desde el tentativo al efectivo, buscar SIEMPRE el primer hueco vacío, no añadir al final.
21. **Columna "Para":** En el menú tentativo, mostrar claramente qué comensales pueden comer cada plato (basado en preferencias/exclusivos).
